# design_editor.md — Редактор рига (`tools/rig_editor.html`) и передача в игру

> Полная спецификация **standalone-редактора рига** и **конвейера «редактор → игра»**.
> Реализация: `tools/rig_editor.html` (редактор), `rigbridge.js` + `rig-core.js` (приём в
> игре). Ссылка из `CLAUDE.md` (строки `tools/rig_editor.html`, `rigbridge.js`, `rig-core.js`).
> Локомоция самих ног (IK) описана отдельно — см. `design_legs.md`.

## 1. Назначение и запуск

Редактор — отдельная HTML-страница, в которой авторят **внешний вид юнита**: расстановку
деталей/модулей, скелет ног и спрайты-ассеты. Игру он **не** изменяет напрямую — результат
переносится отдельной кнопкой (см. §11).

- **Открывать через превью-сервер:** `http://localhost:8123/tools/rig_editor.html` (нужен
  один origin с игрой для localStorage-моста; см. §11).
- Переиспользует модули игры: `constants`, `unitdefs`, `anim`, `rig`, `render_parts`
  (+ `render_ring`/`legik` подгружаются по требованию). Скрипты грузятся с cache-busting
  (`?v=Date.now()`) — браузер не подсунет старый `rig.js`/`render_parts.js`.
- К самой игре не подключается (никакого общего состояния, кроме явной передачи снимка).

## 2. Превью, позы и состояния

- Крупный превью юнита в реальном игровом масштабе с зумом (`zoom`, ползунок). Зум — только
  увеличение холста; **дизайн-координаты** деталей от него не зависят.
- **Поза** ←→↑↓ задаёт направление взгляда/бурения (через `dx/dy/faceX`). Для кольца поза
  задаёт `aim` — видно ПОВОРОТ кластера модулей (бур к «дну»/«вбок»).
- **Состояние:** idle / ход / копание / **стоп-статика** / присед.
- Редактирование скелета идёт по СТАТИЧНОЙ позе (`editRig` — резолв с `noAnim`): ручки/драг
  не зависят от фазы анимации (иначе idle-свинг запекался бы в `ang` и нога «уезжала» со
  временем).

## 3. Два режима редактирования (скелет / ассет)

Тумблер `editMode`: «◆ скелет» / «✦ ассет». РАЗДЕЛЯЕТ правки, чтобы не задевать лишнее.

- **СКЕЛЕТ:** канвас тянет только кинематику (позиции `f/s`; у выбранного сегмента ДВА узла —
  жёлтый корень = позиция всей ноги `f/s`, синий стык = угол/длина кости). Колесо НЕ трогает
  спрайт.
- **АССЕТ:** правится только спрайт (зелёная ручка = пивот, колесо = размер, Shift+колесо =
  поворот). Кости неприкосновенны.
- Поля неактивного режима в панели приглушены (CSS `rigRow`/`assetRow` по `body.mode-asset`).

## 4. Тайл-сетка и калибровка масштаба

Кнопка «⊞ тайл-сетка» (только в СКЕЛЕТЕ):

- ПОЛ↔ПОТОЛОК = ОДИН игровой тайл (`tilePx = floorY - ceilY`). На фоне — ПОЛНАЯ тайл-сетка
  этого шага (анкер `floorY`/`x=0`).
- Тяни ПОТОЛОК = масштаб тайла (сетка масштабируется), тяни ПОЛ = сдвиг сетки. Состояние в
  localStorage (`rigGuide`).
- `unitMetrics()`: `scale = TILE/tilePx` — готовый **`UNIT_DRAW_SCALE`** (юнит займёт ту же
  долю тайла, что в редакторе, независимо от абсолютного размера рига) + `footTiles` (стопы
  над линией пола, в тайлах).
- Внизу линейки readout: «1 тайл = …px · юнит ×scale · стопы …т над полом».
- Метрики `placement: {tilePx, scale, footTiles, guide}` сохраняются в проект-JSON (и
  восстанавливают линейку при загрузке) + пишутся комментарием в экспорт блупринта.
- **`scale` РЕАЛЬНО управляет размером юнита в игре:** при «→ В ИГРУ» он кладётся в
  `def.drawScale`, а игра берёт его через `unitDrawScale(unit)` (см. §13). Передвинул
  пол/потолок → перетолкнул в игру → перезагрузил → юнит стал крупнее/мельче.
- **Линия ПОЛА управляет высотой над поверхностью:** при «→ В ИГРУ» пишется
  `def.footAnchor = floorY/tilePx` (центр корпуса → линия пола, в тайлах). Игра ставит юнит на
  эту высоту над полом, чтобы ОТМАСШТАБИРОВАННЫЕ ноги доставали поверхность (иначе мелкий юнит
  «парит» — фикс. stand-лифт не скейлится). Поэтому **ставь линию пола ровно по стопам**.

## 5. Карточки деталей

Список деталей справа. Карточка несёт:

- Драг слота + поля `f/s/z/need` + тумблер «проц» (рисовать ли процедуру) + ассет.
- **Добавление/удаление** деталей: двигатель / оружие / кастом / нога / …
- **«+ пара ног»** = две зеркальные ноги (галка «зеркало»).
- У ног — под-карточки **сегментов**: `ang`/`swing`(`sw`)/`len`/`z` + ассет на сегмент +
  пивот (`offX`/`offY`/колесо), «+ сегмент». `sw` = размах качания при ходьбе/idle (0 жёстко,
  1 полный, − противофаза).
- Кабели.

Сегмент ищется по ДЕФ-индексу (`sg.idx`), т.к. `leg.segs` отсортирован по z (позиция в
массиве ≠ порядок определения).

## 6. Ручки на канвасе (выбор и правка сегмента)

Сегмент выбирается кликом ПРЯМО ПО НЕМУ на холсте (`nearestLegSeg`) ИЛИ по его `<b>` в панели.
На стыках всех ног — слабые синие маркеры-подсказки.

- **синий КРУГ на стыке** — тянет угол + длину (`ang`/`len`).
- **зелёный КВАДРАТ на корне** — пивот/выравнивание спрайта (`offX`/`offY` через обратный
  поворот; по умолчанию = корень, т.е. на ПРОТИВОПОЛОЖНОМ конце кости от синего).
- **колесо** — масштаб спрайта сегмента. **Shift+колесо** или поле `пов°` — поворот СПРАЙТА
  (отдельно от угла кости `ang`; хранится в `PART_SPRITES.rot`/`PART_SPRITE_SRC.rot`,
  экспортится).
- Кость между ручками — пунктир (не хват). При выборе сегмента прочие точки
  (масс-детали/хаб/маркеры) ПРИГЛУШАЮТСЯ — ручки не путаются; хит-тест берёт ближайшую ручку
  (круг vs квадрат — разные формы).

## 7. IK-превью щупалец

Кнопка «⊕ IK-превью» (грузит `legik`):

- Мини-симуляция ТЕМ ЖЕ движком, что в игре. ФЕЙКОВЫЙ мир по табу-кейсу
  (`коридор`/`пол`/`стена`/`потолок`) + юнит «шагает»/«карабкается» сам (тумблер «ходьба»).
- Видно ходьбу/лазание и доводку спрайтов НА СЕГМЕНТАХ (пивот/масштаб/поворот правятся в
  карточках сегментов, видны сразу; длины сегментов — пересборка по подписи `ikSig`).
- Корпус едет на ногах (`bodyOff`).
- Сегментные спрайты в `legik.drawLegRig` рисуются ТОЙ ЖЕ схемой, что FK `drawLeg`
  (`sp.px/py/w/h`, `rotate(ang − π/2 + rot)`) — IK-превью совпадает с FK по
  масштабу/повороту/пивоту.
- В редакторе `legConfigsFromUnit(unit)` зовётся БЕЗ `scale` (=1) — масштаб даёт общий
  `ctx.scale(zoom)`. (В игре передаётся `UNIT_DRAW_SCALE`, см. §12.)

## 8. Ассеты (спрайты)

- Загрузка PNG на деталь/сегмент (live-превью на риге, масштаб колесом, сдвиг пивота).
- **Удаление фона** (`processImage`): «палочка» / «хром» / нет + допуск (`tol`).
- **Raw-PNG храним специально** (не processImage-результат), чтобы потом можно было менять
  метод/допуск удаления фона.
- **Ассет-кабель** — один на все, тянется по A→B.
- Канвас на всю область (нет кропа).

## 9. Юнит-КОЛЬЦО (`kind:'ring'`, корпус `core`)

Когда выбран ring-корпус — отдельная ветка рендера (`drawRingEditor`, грузит `render_ring`):
ноги (FK) ПОД, тор-реактор в центре, модули по окружности.

- **Модули** заданы `ang°` + `rad` (в долях R), ориентированы НАРУЖУ. Тянутся мышью →
  пишут `ang`/`rad` (БЕЗ `aim`). Карточки модулей показывают `ang`/`rad` вместо `f/s` (ноги —
  как обычно, `f/s` + сегменты).
- Поза ←→↑↓ задаёт `aim` → видно ПОВОРОТ кластера.
- **Кольцо-реактор** = деталь `kind:'reactor'` в центре (`ang/rad`=0, не вращается),
  исключена из вращающихся модулей. Рисуется `drawRingCore`: спрайт если `!partsProcOn()`,
  иначе процедурный тор `drawReactorRing`.
- **Карточка реактора — ДВА ассета:** `reactor` (ВКЛ, по умолчанию) + `reactor:off` (ВЫКЛ,
  для будущих фич) + тумблер превью вкл/выкл (`unit.reactorOn`). Оба экспортятся в
  `PART_SPRITE_SRC`. Пивот реактора по умолчанию ПО ЦЕНТРУ (`offX=offY=0` → центр спрайта =
  центр юнита, как процедурный тор); ПОЛОЖЕНИЕ правится полями `offX/offY` ИЛИ перетаскиванием
  ЗЕЛЁНОГО квадрата на канвасе (режим «ассет», `reactorDrag`: `offX/offY` = центр спрайта в
  дизайн-координатах от центра).
- **«ассеты → всем ногам»** (кнопка на карточке ноги): копирует спрайты + конфиг сегментов
  этой ноги на ОСТАЛЬНЫЕ ноги (сопоставление по id сегмента) — поставил ассеты одной ноге,
  разнёс на все.
- z-индекс реактора/модулей/сегментов работает (единый порядок).
- Экспорт даёт `kind:'ring', ringR, parts:[{…, ang, rad, …}]`.

## 10. Проект (снимок сцены в один JSON)

Секция «Проект» сверху.

- **«💾 сохранить»** скачивает `<hull>-rig.json`:
  ```
  { format:'twilight-rig/v1', hull,
    def: UNIT_DEFS[hull],
    placement: { tilePx, scale, footTiles, guide },
    assets: { [id]: { src:<raw-PNG как data:URI>, file, method, tol, scale, offX, offY, rot } } }
  ```
- **«📂 загрузить»** (file input) перезаписывает текущую сцену из такого JSON. ⚠️ Загруженный `def`
  применяется СО СЛИЯНИЕМ базовой структуры: недостающие базовые детали из `unitdefs.js` (снимок
  `BASE_PARTS` на старте редактора, ПО `id`) дописываются в `def.parts`. Так старый файл без новой
  базовой детали (напр. `aux` доп-слот) всё равно получает её — структура деталей всегда из редактора.
- При загрузке ассеты маршрутизируются по типу блока: реактор (вкл/выкл) — по `data-akey`
  (`data-sk`); сегмент ноги — по `data-seg` (`data-sk`); обычная деталь — по `.part[data-id]`
  (`data-k`). NB: ключ реактора БЕЗ двоеточия (`reactor`) когда-то уходил в ветку обычной
  детали и крашился на отсутствующих `data-k`-полях — реактор ВКЛ не грузился. Маршрутизация
  с null-гардами это чинит.

## 11. Передача в игру («→ В ИГРУ»)

Кнопка в секции «Проект». Делает **два** пути одновременно (см. §13 про разницу origin):

1. **Файловый (главный, работает на `file://`):** СКАЧИВАЕТ самодостаточный `rig-<hull>.js` —
   IIFE с блупринтом + обработанными спрайтами как `data:URI` (`setPartSprite('<hull>:id', …)`) +
   снятием процедурного дебага. В `def` вшиты **`drawScale`** = `unitMetrics().scale` и **`footAnchor`** =
   `floorY/tilePx` из тайл-сетки. ⚠️ Применяется **СЛИЯНИЕМ**, а НЕ полной заменой: базовые детали из
   `unitdefs.js` (которые загрузились ДО `rig-core.js`), отсутствующие в авторском `def` ПО `id`, дописываются
   в `def.parts`. Так НОВАЯ деталь в `unitdefs.js` (напр. `aux` доп-слот) не теряется старым экспортом — её
   видно сразу (процедурно), а спрайт авторишь и перевыкатываешь файл позже. Кладёшь файл в КОРЕНЬ проекта
   ПОВЕРХ заглушки (`rig-core.js`) и перезагружаешь игру.
2. **localStorage (для игры с того же сервера):** пишет тот же снимок в
   `localStorage['twilight-rig:<hull>']`. «стереть из игры» чистит localStorage.

### Приём в игре

- **`rig-core.js`** — файловый снимок, грузится ПОСЛЕ `rigbridge`, ДО `game`. В репозитории —
  ЗАГЛУШКА (no-op). Перезаписывается скачанным `rig-<hull>.js`. **Работает на `file://`**
  (двойной клик `index.html`). По одному файлу на корпус (`rig-core.js`; при втором корпусе
  добавь `rig-<hull>.js` в загрузчик `index.html` + заглушку).
- **`rigbridge.js`** — localStorage-мост, грузится ПОСЛЕ `tentacles`, ДО `game`. Читает
  `localStorage['twilight-rig:<hull>']`: оверрайд `UNIT_DEFS[hull]` + спрайты в
  `PART_SPRITES['<hull>:*']`. Если пришли спрайты — снимает процедурный дебаг
  (`partsProcedural(false)`/`legikProcedural(false)`).

### Почему два пути — РАЗНЫЕ origin

`localStorage` per-origin. Игра открывается **двойным кликом** `index.html` (`file://`),
редактор — с превью-сервера (`http://localhost:8123`). Это РАЗНЫЕ origin → localStorage НЕ
делится → `rigbridge` на `file://` молчит. Поэтому главный путь — файловый (`rig-core.js`).
localStorage-мост срабатывает только если ИГРА тоже открыта с того же сервера
(`http://localhost:8123/index.html`) — тогда достаточно «→ В ИГРУ» + reload, без перекладывания
файла.

## 12. Экспорт кода (ручной)

Кроме снимка-проекта/«в игру», есть экспорт исходников:

- Блупринт для `unitdefs.js` (с комментарием `placement` из §4).
- `PART_SPRITE_SRC` (для игры) — ключи namespaced по корпусу `<hull>:<id>`, пути к ассетам
  ОТНОСИТЕЛЬНЫЕ (`assets/parts/…`), без локальных путей.

## 13. Как редактор-данные ложатся в игру (инварианты)

- **Namespacing по корпусу (без гонок):** ключ спрайта `PART_SPRITES['<hull>:<id>']`. Рендер
  ставит `partsHull(unit.hull)`, `spriteFor(id)` ищет `<hull>:id` с откатом на плоский `id`
  (для редактора — он авторит один корпус плоскими ключами). `core` и `scout` НЕ делят ассеты.
- **Размер юнита — `unitDrawScale(unit)`:** = `UNIT_DEFS[hull].drawScale` (вшит редактором из
  тайл-сетки, `=TILE/tilePx`) ИЛИ дефолт `UNIT_DRAW_SCALE`. Его берут ВСЕ потребители отрисовки
  (кольцо, FK-корпус, ноги-щупальца, прожектор, заставка-печать) — поэтому калибровка
  пол/потолок в редакторе РЕАЛЬНО меняет размер юнита в игре (а не игнорируется). Передвинул
  сетку → «→ В ИГРУ» → перезагрузил.
- **Масштаб применяется единым transform** (значение = `unitDrawScale`):
  - Кольцо (`drawRingUnit`): один `ctx.scale(opts.scale)` на всё — позиции И размеры спрайтов
    ужимаются вместе (как `ctx.scale(zoom)` в редакторе). Иначе `drawPart` рисует спрайт в
    абсолютных `sp.w` px (игнорируя `S`), и спрайты выходят в `1/UNIT_DRAW_SCALE`≈1.6× крупнее
    относительно кольца, чем в редакторе.
  - Ноги (`legik`): игра передаёт `legConfigsFromUnit(unit, UNIT_DRAW_SCALE)` → hip И длины
    сегментов масштабируются вместе с корпусом/кольцом. Иначе крепления ног уезжают в
    `1/UNIT_DRAW_SCALE` раз дальше, чем рисуется кольцо (ноги «отрываются» от корпуса). Редактор
    зовёт без `scale` (=1) — у него свой `zoom`.
  - Спрайты сегментов ног: `makeLegRig(configs, UNIT_DRAW_SCALE)` кладёт `rig.drawScale`, и
    `drawLegRig` ужимает спрайт (`ctx.scale(drawScale)` перед `drawImage`) ВМЕСТЕ с костью —
    иначе `drawImage` рисует абсолютные `sp.w/sp.h`, и спрайт не совпадает с укороченной костью
    (сегменты «не на месте»). Пивот/поворот спрайта при этом сохраняются.
- **Посадка на поверхность — `def.footAnchor`** (центр→линия-пола в тайлах из тайл-сетки):
  `tentacles.updateTentacles` ставит якорь `D = TILE·(0.5+LEGIK_STAND − footAnchor)` вдоль «к опоре»
  (`−up` по `supportAngle`: пол → вниз, стена → к стене, потолок → вверх) — корпус садится так, что
  отмасштабированные ноги достают ЛЮБУЮ поверхность. Дефолт (нет `footAnchor`) = `0.5+LEGIK_STAND`
  → `D=0` (старое поведение). Без этого мелкий юнит «парил» на всех опорах: фикс. stand-лифт
  `LEGIK_STAND` в тайлах не скейлится, ноги ужаты — не доставали фикс. дистанцию центр-тайла→поверхность.
  Линию пола в редакторе ставь по стопам — она же калибрует посадку и на стене/потолке.
- Поэтому **то, что видно в редакторе (при калибровке тайл-сеткой), совпадает с игрой** по
  пропорциям И по посадке: реактор/модули/ноги садятся на кольцо и на пол/стену/потолок одинаково.

## 14. Гочи и чек-лист

- Имена ассетов — ОТНОСИТЕЛЬНО корня проекта (`assets/parts/…`), без локальных путей.
- Спрайты больших нативных размеров как `data:URI` могут раздуть localStorage (квота ~5 МБ);
  файловый путь (`rig-core.js`) от квоты не зависит — это ещё одна причина предпочитать его.
- После «→ В ИГРУ»: положить `rig-<hull>.js` в корень (поверх заглушки) и ПЕРЕЗАГРУЗИТЬ игру
  (мост/файл читаются один раз при загрузке).
- Проверять результат в самой игре (а не только в IK-превью редактора): пропорции
  кольца/ног/реактора, конус прожектора, окклюзия за породой.

## 15. Ассеты ВАРИАНТОВ модулей (в карточке детали — системно, без правок кода)

Спрайт на КОНКРЕТНЫЙ вариант модуля слота (а не общий спрайт детали). Чтобы варианты одного слота
выглядели по-разному (`cargo` vs `cargo_repair`, будущие буры), БЕЗ правок кода на каждый модуль.

- **Реестр — `MODULE_DEFS`** (constants.js, единый источник). Загрузка ассетов вариантов — НЕ отдельной
  секцией, а **под-списком ПРЯМО В КАРТОЧКЕ ДЕТАЛИ-СЛОТА** (`buildPartVariants`/`buildModRow` в
  `rebuildParts`): деталь корпуса (kind) → категория (`PART2CAT`) → модули этой категории. **Дефолтный
  модуль `[0]` = сама деталь** (грузить нечего); показываются ТОЛЬКО НЕ-дефолтные варианты `[1..]`.
  Добавил вариант в `MODULE_DEFS` → он сам появился под нужной деталью, ничего больше не правишь.
  (Деталь без вариантов — бур/двигатель/сенсор — под-списка не имеет.)
- **Ключ спрайта — `<hull>:mod:<moduleId>`** (в редакторе авторится плоско `mod:<id>`, как и детали).
  Под-строка варианта: загрузка PNG + удаление фона (method/tol) + `scale/offX/offY/rot` + thumbnail
  (загруженный спрайт = индикатор «ассет есть») + **«превью»** (ставит модуль в слот
  `unit.modules[category]=id` → корпус показывает его спрайт; кнопка зеленеет, пока активна).
  ⚠️ Превью работает, ТОЛЬКО потому что **все `drawPart` редактора идут через `modOpts(p)`** (он зовёт
  `partSpriteId`, как игра) — у редактора СВОЙ рендер (`draw`/`drawRingEditor`/`drawIKScene`), не игровой
  `drawRingUnit`; рефакторишь рендер редактора — не потеряй `modOpts`, иначе превью молча сломается.
- **Экспорт «↓ module_assets.js»** (в секции «Экспорт») — самодостаточный манифест в КОРЕНЬ проекта
  (как `rig-<hull>.js`): `MODULE_SPRITE_SRC = { '<hull>:mod:<id>': {url:<data:URI>, scale, offX, offY,
  rot} }` + загрузчик (`new Image()`→`setPartSprite`). `<script>` ПОСЛЕ `render_parts`, ДО `game` (file:// ок).
- **Приём в игре:** `render_parts.partSpriteId(unit, partId)` — деталь корпуса (kind) → слот-категория
  (`PART2CAT`) → установленный модуль (`unit.modules`) → если есть `spriteFor('mod:<id>')`, рисуем его,
  иначе обычный спрайт детали. Потребители: корпус-кольцо/FK (`drawRingUnit`/`drawTachikoma`) и галерея
  сборки (`inventory._drawCard`: `mod:<id>` → спрайт детали категории → проц-иконка). `unit.modules`
  ставит `game.startSession` (из `inventory.modules`); превью сборки — `inventory._dummyUnit`.
- **Проект-JSON** сохраняет/грузит `mod:<id>`-ассеты вместе с остальными (`saveProject`/`loadProject`
  маршрутят их в `.modcard`).
